## 验证码逆向分析（2026-10-10 22:10，重要参考资料）

### 确认服务端用的库：**github.com/mojocn/base64Captcha**

证据：所有响应都带 `set-cookie: __ct_cya_ckt=...`，这是该库的标志。

### 关键源码事实（clone 仓库逐行确认）

| 项 | 事实 | 对 OCR 的意义 |
|---|---|---|
| 干扰结构 | `strikeThrough`（正弦横线，幅度 5-20，周期 80-180）+ `fillWithCircles`（背景圆点）+ `distort`（全局正弦位移，幅度 5-10） | 三重干扰叠加 |
| **字符颜色** | `drawCircle(..., 1)` —— **调色板索引固定**，全图字符同色 | 颜色可作分割依据 |
| **干扰线颜色** | 同样用索引 1，但 `radius = r/2`（**圆点半径只有字符的一半**） | 粗细可区分 |
| 背景圆点 | `colorIdx = randIntRange(1, dotCount-1)`，亮度由 `randomBrightness(prim,255)` 生成 | 亮度分层 |
| 默认参数 | `NewDriverDigit(80, 240, 5, 0.7, 80)` = 高80 宽240 **5位** | EasyFrp 改成了 120x40 / 4位 |
| 字体 | `digitFontData` 是**硬编码 11×18 点阵位图**（fonts.go，非 TTF） | 可精确导出模板 |
| 排列 | **等距**：`x += width + dotSize` | 切分有强先验 |
| 几何 | `digitFontWidth=11, digitFontHeight=18`；120x40/4位时 `dotSize=1`，字符 12×20 | 可精确反推 |

已从 `fonts.go` 提取全部 10 个 11×18 点阵字模（`digit 0-9`，各 198 像素值），
存于 `ef_digit_font.json`（若需要可重新从仓库提取）。

### 实测 EasyFrp 图形特征（120×40，4 位）

6 倍放大观察 + 像素统计结论：
- **字符**：深色、高饱和、粗体，笔画半宽 p50=3 / p90=7（6倍图坐标）
- **干扰线**：浅色、低饱和、细线
- 但**笔画宽度与干扰线重叠** —— 距离变换/形态学开运算均无法可靠分离
  （试过 `S>=100,k=25` 开运算 → 只剩边缘碎片；`dist>=8` → 同）
- 颜色聚类也不行：暗像素色相集中在 H=2/21 两处（字符深红/深绿），但**同色相的干扰线共存**

### 为什么现成项目都不行

EasyFrp 的参数组合（120×40 小尺寸 + 4 位 + 浅色细线 + 深色粗体字符）
落在所有公开 OCR 训练分布之外：ddddocr 训练集多为"深色干扰线 + 细体字符"，
正好相反。**这不是换个 OCR 库能解决的，是需要针对该站点重训数据。**

### 若将来要做自动化，建议路径（按性价比）

1. **重标数据集**（前提）：现有 72 张标注约 30% 有误，且需覆盖 EasyFrp 真实难度
2. **用 base64Captcha 自己生成训练图**：既然库是开源的，可用 Go 跑
   `NewDriverDigit(40, 120, 4, 0.7, N)` + 相同字体批量生成**带真值标签**的样本
   —— 这是本项目最有价值的可复用资产，可无限量生成精准标注数据
3. 拿这些数据训轻量 CRNN，或微调 ddddocr

### 已确认：EasyFrp 用的**就是**这个点阵 driver

6 倍放大 + 像素级验证：
- 字符区域**抗锯齿像素仅 0.5%**，最暗像素值 61（非 0），灰度级 133 种
  → 边缘无平滑过渡 = **硬边点阵渲染**（base64Captcha 用 `SetColorIndex` 逐点画）
- 这与从 `fonts.go` 导出的 11×18 点阵字模（`ef_digit_font.json`）**完全吻合**

**结论：方向是对的，点阵模板匹配本该可行。**
之前失败不是"模板匹配不适合"，而是**掩膜提取没做对**（没能把干扰线从字符里分离干净）。

### 掩膜提取的实测数据（这是关键卡点）

字符：深色、高饱和、粗体，笔画半宽 p50=3 / p90=7（6倍图坐标）
干扰线：浅色、低饱和、细线

试过并**失败**的方法：
| 方法 | 结果 |
|---|---|
| HSV 阈值 `S>=55,V<=225` | 掩膜覆盖 88% 列 → 线全被当字符 |
| 形态学横向开运算 `S>=100,k=25` | 只剩边缘碎片（字符被吃掉） |
| 距离变换 `dist>=8` | 同上，只剩碎片 |
| 颜色聚类（色相 H=2/21） | 同色相的干扰线与字符共存，无法区分 |

**症结**：字符笔画半宽（p50=3）与干扰线宽度**重叠**，单纯的"粗细"或"颜色"单一特征都分不开。
需要的是**颜色 + 粗细联合判据**，或利用"字符等距排列"这个强先验做联合约束求解。

- 上表的源码参数（`dotSize`、字符尺寸、等距排列）可用于精确建模

  （开源库 + 已知答案 = 无限量精准标注数据），再训轻量 CRNN

## ✅ OCR 自动化 —— 已解决（2026-10-11 最终结论）

> **⚠️ 本文档早前"宿主机 ddddocr 仅 29%、不达标、已停用"的结论是错的。**
> 下面是纠正后的完整结论，**不要再走自研 OCR 的老路**。

**错误从哪来**：那 29% 是拿 `ef_samples/` 72 张**人工标注**样本测出来的，
而这批标注本身约 30% 有误（密集干扰线下批量目视，细笔画 `1`/`7`/`4` 看错）。
**用坏的 ground truth 去评判 OCR，会把 ddddocr 的正确识别也算成错** ——
于是得出假结论，白白放弃了一条本来完全可用的路线。

**正确方法：让服务端当裁判（评估成本降为 0）**

登录接口 `POST /v1/auth/login` **先校验验证码、再校验密码**，且 `captchaKey`
一次性但**可重复提交**。于是：

> 提交后只要服务端不返回「验证码错误」，就说明 OCR 的答案是对的。

这把"需要人工标注数据集"的问题变成了**全自动可测**的问题，不再依赖任何人肉眼判读。

**关键发现：ddddocr 的输出可二分**

32 张真实图上逐张用服务端验证（宿主机 ddddocr 1.6.1）：

| 预处理通道 | 输出「4位纯数字」占比 | 其中正确率 | 输出非4位时正确率 |
|---|---|---|---|
| raw（原图直送） | 75.0% | **100.0%** (24/24) | 0% (0/8) |
| bright（亮度分离去彩线） | 90.6% | **96.6%** (28/29) | 0% (0/3) |

**规律**：ddddocr 能给出 4 位纯数字时几乎必对；一旦输出含字母或位数不对，**必然错**。

→ 策略：**只在服务标记 `clean` 时才提交，`clean=false` 就换图** ——
既不浪费提交轮次，也不会把错误答案送出去。

### 关键发现：**评估基准本身不可靠**

放大 6 倍逐张核对后确认，**双方都有错，但错法不同**：

| 样本 | 我标注 | ddddocr | 真相（6倍放大确认） |
|---|---|---|---|
| cap05 | 2314 ❌ | 2668 | **2668**（ddddocr 对） |
| cap06 | 2668 ❌ | 8810 | **8810**（ddddocr 对） |
| cap09 | 0638 ❌ | 6593 | **6593**（ddddocr 对） |
| cap73 | 3513 | `3+513` | **3513**（我 对，ddddocr 把干扰线当字符） |
| cap38 | 3526 | `1=04` | **3526**（我 对） |
| cap30 | 3580 | `200` | **3580**（我 对，ddddocr 丢字符） |

- **早期标注（cap00-11 那批）确有错** —— 当时批量目视，在密集干扰线下把细笔画字符（`1`/`7`/`4`）看错。
- **ddddocr 的"失败"其实是它在自曝不确定**：输出长度 ≠ 4（`231`/`200`/`144`）、含非数字（`o638`/`3+513`/`1=04`）。
  后来用服务端 oracle 大量实测才确认：**这类输出 100% 是错的，而 4 位纯数字输出 100% 是对的** ——
  这正好可以当免费的高置信度信号用（见上表策略）。

### 落地实现与端到端实测

**1) 宿主机双通道 OCR 服务** `ef_ocr_service.py`
（systemd 常驻 `ef-ocr.service`，监听 `0.0.0.0:13003`，容器经 docker0 网关 `172.17.0.1` 访问）

- 通道 1 `raw`：原图直送 ddddocr
- 通道 2 `bright`：亮度门限 `lum < 130` 去掉彩色干扰线后再送（干扰线普遍比字符亮）
- 返回 `{ok, text, clean, channels:{raw:{text,clean}, bright:{text,clean}, ms}}`
- **只有能给出「4 位纯数字」的通道才置 `clean=true`**，raw 优先

**2) 青龙脚本 `EasyFrp签到.py`**
- `EF_OCR_URL` 指向该服务；收到 `clean=false` → 返回 `ocr_unsure` **换图**而不是乱猜
- 连续 `EF_UNSURE_MAX`（默认 8）轮仍不确定 → 强制提交最佳候选（防服务异常时空转）
- 修掉一个隐藏 bug：原先"本地 cv2 缺失"就降级人工过码 —— 容器 Alpine 本就没 cv2，
  会直接把主力 OCR 通道废掉。现在只有"本地 cv2 缺失**且**没配 `EF_OCR_URL`"才降级。

## 走过的弯路（避免重复踩坑）

| 尝试 | 结果 | 教训 |
|---|---|---|
| 连通域过滤切分 | 8/12 张切错 | 字符被线切断/粘连时，连通域几何特征不可靠 |
| 竖直投影直接 DP | 退化成均分 | 前缀和使切分点边际收益恒为 0，必须加宽度惩罚 + 低墨奖励 |
| 滑窗模板匹配 + 全局指派 | 训练集 0/12 | 掩膜尺度/极性与模板不匹配，且指派逻辑掩盖了切分问题 |
| 结构特征加权（NCC+密度+连通域） | 0/20 | 手工权重把纯 NCC 信号拉偏，不如纯形状匹配 |
| 形态学细线抑制 | 字符被一起抹掉 | "实心块判定"失效；细线穿过字符时与字符同连通域 |
| 形态学开运算（MinFilter/MaxFilter） | 比原图更糊 | 腐蚀+膨胀把字符与干扰线糊成一团，可读性反而下降 |
| 颜色聚类"提取字符" | 70% 能分离出 4 个 | 判据过严会漏浅色字符；"擦线"比"提字"更稳 |
| 亮度门限单通道 | 85%（对比原图 80%） | ✅ 有效，后来成为 bright 通道 |
| **拿人工标注样本评估 OCR** | 测出 29% 的假数据 | ⚠️ **本项目最大的坑**：密集干扰线下人工标注错误率约 30%，拿它当基准会把正确结果判成错的 |
| 据坏基准给 ddddocr 判死刑 | 白白停用一条可用路线 | 教训：**评估方法错，结论就全错** |
| 11 变体投票 | 28%（无提升） | 在坏基准下测得，"稳定地错"的结论同样不可信 |
| 用 ddddocr 反向"修正"标注 | 71% 不一致 | 同上，坏基准下的判断 |
| **服务端 oracle + 双通道 + clean 门控** | **93.3% clean / 命中 100% / 平均 1.07 张图** | ✅ **最终方案** |

**根本教训（两句话）**：

1. 这类验证码真正的突破口**不是更花哨的 CV，而是找对评估方法**。当服务端可当 oracle 时，
   应**先用它把真实准确率测准**，再决定要不要上 ML ——
   之前数小时的自研 OCR 攻坚，方向从一开始就被坏基准带偏了。
2. 自研 cv2「分割 → 切分 → 模板匹配」在干扰线与字符**像素级交织**时天花板极低
   （训练集 100% / 线上 0%），**不值得再投入**。


## 部署要点（踩过的坑）

- 容器是 Alpine musl：`onnxruntime` / `opencv-python-headless` 都无 wheel
- `/usr/bin/python3`（py3.12）pip 坏了（pyexpat 符号冲突）；**`/usr/local/bin/python3`（py3.11）才可用**；cv2 只在 py3.12 那个里
- 传文件到容器：`docker cp` 不认 Windows 路径 → **SFTP 传到宿主机 `/tmp`**（纯 ASCII 文件名）→ `docker cp` 进容器
- 中文文件名 + `echo base64 >` 会写失败；SFTP 最稳
- 大 payload（>~500KB）会断连，别用 base64 分块
- 青龙 `/api/crons/disable|enable` 的 body 必须是**数字数组** `{"ids":[659]}`，字符串数组 400
